# Clipboard history plan

Prepared 2026-09-23 against `aae2c1f` (Codenotch 1.17.0).
Status: phases 1–4 implemented on `clipboard-history`. The pasteboard
permission prompt is still to be checked by hand on a real Mac (phase 5).

## What the user chose

1. A clipboard control on the notch opens a panel listing clipboard history;
   clicking an entry puts it back on the clipboard, ready for ⌘V.
2. Text, rich text, images and files are all in scope for the first increment.
3. The control is a cell at the end of the stack, after every account cell
   (the accounts configured in Settings › Accounts).
4. The feature is off until switched on in Settings.
5. History is kept across quits.

## Behaviour

### The clipboard cell

- A stack cell with a clipboard glyph, not a ring — it measures nothing.
- Always the last cell, after every account cell, whatever order the user
  gives the accounts in Settings › Accounts. It is not itself in that list.
- Its settings-orb end stays where it is: the orb hangs past the foot of the
  stack, which is now the clipboard cell.
- Hover shows the pointing hand and no usage tooltip. A click toggles the
  panel (where a provider cell would refetch).
- Absent entirely while the feature is off, so the stack is unchanged for
  everyone who never enables it.

### The panel

- Opens where the tooltip does, away from the bezel
  (`NotchEdge.tooltipDirection`): to the left on the default right edge,
  below the notch on the top edge, and so on. Never over the bezel.
- While it is open, provider tooltips are suppressed and the notch stays
  expanded; it closes on a second click on the cell, a click elsewhere,
  after picking an entry, or when the notch folds.
- A scrolling list, newest first. Each row: a preview, the source app's icon
  and "2 min ago".
  - **Text** — two lines, trimmed.
  - **Rich text** — the plain-text rendering plus a small "Rich text" badge.
  - **Image** — a thumbnail and its pixel size.
  - **Files** — the Finder icon and name of the first, "+N more" for the rest;
    a row whose files no longer exist is dimmed and cannot be picked.
- Click a row → every stored representation is written back to the general
  pasteboard, the row moves to the top, a short "Copied" confirms, the panel
  closes. The notch never takes focus (`NotchPanel.canBecomeKey == false`),
  so the app the user was in still has it and ⌘V pastes immediately.
- Hovering a row reveals a remove button; the footer has **Clear history**.

### Capture

- Poll `NSPasteboard.general.changeCount` every 0.5 s while the feature is on;
  read contents only when the count moves. macOS offers no change
  notification.
- Store, per pasteboard item, the representations in an allow-list:
  `public.utf8-plain-text`, `public.url`, `public.rtf`, `com.apple.flat-rtfd`,
  `public.html`, `public.png`, `public.tiff`, `public.file-url`. Anything else
  is dropped rather than stored opaquely. TIFF is converted to PNG on capture
  (a copied screenshot as TIFF is several times larger).
- **Skip** anything carrying `org.nspasteboard.ConcealedType`,
  `org.nspasteboard.TransientType` or `org.nspasteboard.AutoGeneratedType` —
  the convention password managers and macOS's own AutoFill follow.
- **Deduplicate** on a hash of the stored representations: a repeat copy moves
  the existing entry to the top.
- Codenotch's own write when an entry is picked records the resulting
  `changeCount` and is not captured again.
- Files are stored as references (their URLs), not copies. The app is not
  sandboxed, so no security-scoped bookmarks are needed.
- Limits: entry count (25 / **50** / 100 / 200 in Settings), 20 MB per entry
  (larger ones are skipped), 250 MB on disk in total, oldest evicted first.

### Persistence

- `~/Library/Application Support/Codenotch/Clipboard/`, mode `0700`:
  `history.json` (metadata and order) and `items/<uuid>/<type>` blobs.
- Written after each capture, coalesced; loaded at launch when enabled.
- Switching the feature off stops polling **and deletes the directory** —
  off means nothing is kept, the same as switching off a provider forgets its
  readings.
- Never sent over the phone link, never logged (the unified log gets counts
  and types at most, never content).

### Settings › Clipboard

- **Keep clipboard history** switch, off by default.
- History size, **Clear history**.
- The system's pasteboard permission, see below, with a button to the
  relevant System Settings pane when it is denied.
- Short explanation: what is stored, where, and that password-manager copies
  are skipped.

## The macOS pasteboard permission

The macOS 26 SDK (`NSPasteboard.accessBehavior`, macOS 15.4+) says the default
for the general pasteboard is to **ask** on programmatic access. Access that is
"both user originated and paste related" is exempt; background capture is
neither. So the first capture after enabling the feature raises a system
alert, and the user may later set Codenotch to allow or deny in System
Settings.

- Enabling the switch should explain that macOS will ask, before it does.
- `.alwaysDeny` → the cell shows a disabled state, the panel still lists
  existing history (writing to the pasteboard is not restricted), and
  Settings says why capture has stopped.
- To verify by hand (phase 5): whether reading `changeCount` alone triggers
  the alert (the header implies only content access does), whether `.ask`
  means an alert on every copy, and how the alert behaves for an
  ad-hoc-signed Debug build. Settings › Clipboard shows the current answer
  and links to the pane where it is changed.

The stack today is `snapshots: [ProviderSnapshot]`, and many paths index it
directly — `hoveredIndex`, `cellIndex(along:)`, the click-to-refetch, the reset
alert's lookup. Because the clipboard cell is always last, it needs no cell
enum: geometry counts `cellCount` (providers plus one), and the clipboard cell
is `clipboardIndex == snapshots.count`. Every existing
`snapshots.indices.contains(index)` guard already excludes it, so nothing that
reads a provider can be handed the clipboard cell by mistake.

### Clicks in the panel

The notch window never becomes key. In tests, a SwiftUI tap gesture or
`Button` inside it never fired from a real `NSEvent` sent through the window,
even with mouse events enabled. So the panel does not rely on SwiftUI to take
clicks: it records each row's, remove button's and Clear's frame in the
window's own coordinates (`ClipboardHitTargets`), `NotchPanel.onClickFirst`
offers every left click to the controller before any view sees it, and the
controller answers from those frames — clipped to the list's visible bounds,
remove before pick. VoiceOver acts through accessibility actions instead.
`ClipboardPanelTests.testARowTakesARealClick` drives this with real events.

## Phases

1. **Model and capture** — entry, history, store, monitor; unit tests for the
   filter, dedup, limits, eviction, own-write suppression, persistence round
   trip. Verify the permission behaviour on this Mac.
2. **Stack cell** — geometry counts `cellCount`, then the clipboard cell at
   the end of the stack; check all four edges and three sizes.
3. **Panel** — rows for each kind, pick, remove, clear, closing rules.
4. **Settings, copy, demo** — Clipboard section, translations optional,
   demo fixtures.
5. **Verification** — `make test`; manual pass on each edge copying text from
   an editor, rich text from Safari/Notes, a screenshot to the clipboard,
   files from Finder, and a password from a password manager (must not
   appear); quit and relaunch keeps history; switching off deletes it.

## Not in this increment

- Automatic paste into the frontmost app (needs Accessibility permission and
  synthesised ⌘V).
- Search, pinned entries, per-app exclusions, "paste as plain text".
- Keyboard navigation of the panel (the panel cannot become key).
- Moving the clipboard cell anywhere but the end of the stack.
- Encrypting history at rest.
- The Windows port and the phone app.

## Risks

- **Index-based stack code** — see Implementation; mitigated by doing the
  refactor alone first.
- **Panel size** — the notch window is sized for the tooltip's slack; a list
  with thumbnails may need more depth, which grows the window and its
  click-through region. `updateInteractiveRects` must include the panel or
  clicks fall through to the app beneath.
- **Sensitive data on disk** — persisted history can contain anything a user
  copied that no password manager marked. The Settings copy says so plainly,
  and switching off deletes it.
- **Permission alert** — an unexpected system prompt on first capture if
  enabling the feature does not set the expectation first.
